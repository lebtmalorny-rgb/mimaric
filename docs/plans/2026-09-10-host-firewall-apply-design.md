# Host firewall: дизайн apply и rollback через firewalld

- Дата: 10 сентября 2026 года.
- Статус: **предложение для согласования перед реализацией**.
- Основа: [ADR-0002](../adr/0002-host-firewall.md), Kolla-Ansible `0809` и
  [существующий report](../../integrations/kolla-ansible/host-firewall/README.md).
- Уже согласовано: отдельный playbook, firewalld, сохранение SSH с любых
  источников, отсутствие автоматической установки и запуска firewalld.
- На стенде изменений нет; код apply/rollback пока отсутствует.

## 1. Результат и границы

Тот же `ansible/host-firewall.yml` получает режимы `report`, `apply`, `rollback`.
`report` остаётся режимом по умолчанию. Обычные deploy/reconfigure не запускают
этот playbook. Управление выполняется через firewalld, без записи правил
командами `nft`, `iptables` и без глобального сброса ruleset.
`--check` во всех режимах допускает только чтение и локальный отчёт: без
изменения policy, служебных файлов на хостах, таймеров и reload.

Цель — разрешённые входящие соединения к хосту, затем запрет остальных новых
входящих соединений. Новых ограничений OUTPUT/FORWARD не вводим. Не меняем NAT,
Neutron Security Groups, интерфейсы, маршруты, настройки SSH и HA.
Совместимость с сетью ВМ проверяется отдельно, не выводится из названия INPUT.

Первый профиль реализации: RPM-хосты текущей базы SberLinux 9, systemd,
firewalld с nftables backend и Python bindings, доступными выбранному
интерпретатору помощника. Целевая версия для отдельного тестового профиля —
upstream firewalld 1.3.4; наличие этой версии в DNF search не означает, что она
установлена на Ultra или что сборка поставщика уже проверена.
Непроверенные backend и несовместимый API дают отказ до изменения правил.

## 2. SSH без ограничения источников

SSH-порт разрешается для `0.0.0.0/0` и `::/0`. Не требуется список
административных подсетей. В конфигурации firewalld это отдельное разрешение
TCP-порта без условия source; его нельзя удалить через extra rules.

Номер берётся из подтверждённого inventory-порта `ansible_port`/
`ansible_ssh_port`; если достоверного значения нет, report требует указать его,
а apply отказывает. Порт 22 не подставляется вместо неизвестного нестандартного
порта. При нескольких SSH-listeners требуется явный список дополнительных
SSH-портов, проверяемый так же; другие сервисные порты в этот список не подставляются.

Не меняются аутентификация, ключи, `PermitRootLogin`, `PasswordAuthentication`
и существующие независимые механизмы ограничения доступа. Если чужое правило
мешает согласованному разрешению, сообщается конфликт — оно не удаляется.
«Открытый порт» не означает отключение SSH-аутентификации.

## 3. Собственная область правил

Выбран отдельный объект policy `kolla-host-input` с направлением `ANY → HOST`.
Политики firewalld позволяют адресовать INPUT через egress `HOST`.
[Описание policies](https://firewalld.org/documentation/man-pages/firewalld.policies.html)

У policy фиксируются имя, приоритет и target `CONTINUE`. Набор правил включает
SSH, необходимые базовые протоколы, разрешения из матрицы и завершающий запрет
с более поздним приоритетом rich rule. Приоритеты и совместимость с базовыми
правилами firewalld подтверждаются Linux-тестами до допуска профиля.
Пустой управляемый объект не должен вводить ограничений.

Рассмотрены изменения общей zone и отдельная policy. Zone разделяет конфигурацию
с существующими владельцами; отдельная policy позволяет ограничить область
обновления и восстановления. Прямая запись nftables не выбрана пользователем.

Совпадения имени недостаточно для признания объекта своим: нужны локальная
запись владельца и совпадение ожидаемых свойств/снимка. Коллизия с чужим объектом,
чужая опережающая политика или неизвестное взаимодействие правил блокируют apply.
Не используется глобальный `--runtime-to-permanent`: сохраняется только свой объект.

## 4. Первоначальная подготовка — отдельная явная операция

У firewalld создание permanent policy не означает немедленного появления в
runtime; часть её свойств нельзя менять в runtime. Это нужно отличать от
обычного обновления правил существующей policy.
[Firewalld D-Bus API](https://firewalld.org/documentation/man-pages/firewalld.dbus.html)

Предлагается параметр `host_firewall_initialize: false`. При отсутствии своей
policy обычный apply ничего не создаёт и объясняет необходимость подготовки.
Явный `apply` с `host_firewall_initialize=true` выполняет **только подготовку
пустой policy**, затем завершается без включения запрета. После подготовки
нужны новый report и отдельный обычный apply по новому плану.

Если для подготовки нужен reload, необходим ещё один явный допуск
`host_firewall_allow_initial_reload: true` и согласованное окно работ.
До reload проверяются расхождения runtime/permanent и совместимость с другими
владельцами firewall; неустранённые расхождения блокируют операцию.
Отсутствующий или остановленный firewalld автоматически не устанавливается
и не запускается. Безусловного reload в handler обычного apply не будет.

Подготовка создаёт собственные служебные файлы, но не ограничительную политику.
При её неуспехе восстанавливаются только изменения подготовки, а не полный
снимок чужого firewall. Если безопасное восстановление потребует несогласованного
reload, операция не должна начинаться. Подготовка не считается успешным apply.

## 5. Матрица и допуск к ограничению

Текущий каталог содержит лишь часть API-связей четырёх сервисов. Снять
`APPLY_NOT_IMPLEMENTED` недостаточно: неполное покрытие продолжает блокировать
ограничительное применение. Не вводим `force`, разрешающий игнорировать эти ошибки.

Для каждого выбранного хоста нужны все используемые связи: БД/RPC/координация,
API, Nova/libvirt/миграции, выбранный Neutron backend, хранилища,
PowerOps/Consul/FRR и включённые monitoring/logging-компоненты. Расширение
каталога — обязательная часть готовности выбранного профиля, а не следствие
успешных unit-тестов механизма применения.

Потоки выводятся из проверенных исходников ролей, inventory и эффективных
переменных с учётом overrides. Открытые сокеты сами по себе не создают разрешений.
Внешние источники сервисного доступа задаются явно; разрешение SSH с любых
адресов на них не распространяется. Неизвестный сервис/драйвер, неопределённая
сеть или источник остаются блокировками. Feature flags классифицируются явно,
не считаются автоматически ни сетевым сервисом, ни неважной настройкой.

Report сохраняет план с идентификатором содержимого: выбранные хосты, матрица,
порты, источники, версия каталога, свойства управляемой policy и существенная
конфигурация чужих правил. Счётчики пакетов не входят в сравнение конфигурации.
Apply требует этот идентификатор и повторное чтение состояния; изменение
существенных входных данных требует нового report.

## 6. Применение, проверки и сохранение

Применение выполняется по одному хосту; ошибка запрещает переход к следующему.
Общий сбор сведений о peers делается до последовательного изменения хостов.
Выбранные хосты и адреса исключённых peers не подменяются догадками при `--limit`.

Последовательность для одного хоста:

1. Повторить preflight, проверить план, владение policy и доступность API.
2. Сохранить раздельные снимки своих runtime/permanent настроек и журнал
   транзакции на хосте, с root-владельцем и приватными правами.
3. Подготовить и подтвердить локальный механизм отката по deadline,
   независимый от контроллера и существующей SSH-сессии.
4. Изменить только runtime-правила своей policy; перечитать их и сравнить
   с планом. Нельзя считать серию вызовов firewalld автоматически атомарной.
5. Проверить новое SSH-подключение без повторного использования старого
   multiplex-соединения, обязательные сервисные проверки и разрешённые/
   запрещённые соединения согласно профилю. Проверка открытого TCP-порта
   не заменяет функциональную проверку UDP, миграций или HA.
6. Сохранить только свои permanent-настройки, перечитать их и сверить.
7. Пометить транзакцию подтверждённой и обезвредить откат под общей локальной
   блокировкой. Лишь после этого перейти к следующему хосту.

Если обязательные проверки невозможно выполнить с предусмотренных источников,
фиксации не происходит. Отсутствие источника проверки не считается успехом.
Настройки Kolla `disable_firewall` и `enable_external_api_firewalld`
проверяются на конкурирующее управление; автоматически менять их не предлагается.

## 7. Откат и повторные запуски

Локальный помощник и watchdog/systemd-таймер восстанавливают только свой снимок.
Ansible rescue — дополнительный путь, не единственный механизм восстановления:
при разрыве SSH он может не выполниться. Журнал, снимки и блокировка не зависят
от временного каталога Ansible. Прерывание контроллера не отменяет deadline.

Commit и rollback используют один lock и состояния транзакции: нельзя
одновременно сохранить новую политику и восстановить старую. Просроченная
проверка или повторное подтверждение старого идентификатора отвергаются.
Сбой после записи permanent, но до подтверждения также должен восстанавливать
оба снимка. После незавершённой транзакции новый apply не начинается до
восстановления; reboot-сценарий проверяется отдельно, один transient timer
без персистентного журнала не считается достаточным.

Ручной `rollback` требует конкретный идентификатор транзакции/снимка и проверки
владения. Если объект после снимка изменён посторонним владельцем, нельзя
молча перезаписывать его. Повторный apply уже подтверждённой конфигурации
идемпотентен и не перезапускает firewalld.

## 8. Проверка реализации и эксплуатационный допуск

До реализации нужен отдельный пошаговый implementation plan. В нём фиксируются
точные интерфейсы модулей, схемы транзакций, параметры таймаутов и набор
поддерживаемых сервисных профилей. Это уточнение кода, не разрешение менять
границы SSH, владения или допуск неполной матрицы.

Обязательные группы тестов:

- Полнота матрицы, overrides, IPv4/IPv6, неизвестные данные и защита SSH.
- Firewalld адаптер: реальные поддерживаемые API, ошибки и частичный результат.
- Локальный rollback: потеря контроллера, deadline, гонка commit/rollback,
  повторный запуск, прерывание на каждом шаге и восстановление после reboot.
- Настоящий Ansible: report/check без сетевых изменений, последовательность
  хостов, no-op повтор, невозможность обойти допуск через task selection.
- Изолированный Linux/firewalld: первоначальная подготовка, разрешения и
  запреты, неизменность чужих правил, потеря нового SSH-доступа и откат.
- Наложение на точный архив `0809` и регрессии существующего report.

Unit/fixture-тесты не заменяют Linux-проверку. Доступ к стенду, включение
ограничений, установка пакетов, запуск служб и публикация ветки выполняются
только по отдельному разрешению пользователя.

Откат ограничивает последствия, но не гарантирует отсутствие перерыва.
Он не отменяет fencing, уже вызванный Consul/Masakari из-за изоляции хоста.
Автоматическое подавление HA в этот дизайн не входит.
