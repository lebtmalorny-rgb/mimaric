# Блокировка балансировки Watcher после аварии хоста

При принятии Masakari уведомления `COMPUTE_HOST` с `event=STOPPED` и `host_status=NORMAL` общий запрет останавливает новые расчёты `CONTINUOUS` и допуск новых действий в их планах. Запрет хранится в etcd, переживает перезапуски и снимается только оператором. Исходно балансировка у пользователя не включена; установка этой доработки не создаёт аудитов.

Это первый этап защиты от гонок между аварийным восстановлением и балансировкой по расписанию. Уже допущенное действие может обратиться к Nova после установки запрета и завершиться. Здесь нет ожидания завершения таких действий, Nova drain, отмены миграций, общих блокировок ВМ/хостов, ограничения массовой эвакуации или защиты от каскадной перегрузки. Ручные операции Nova/Mistral и новые `ONESHOT`/`EVENT` планы в этот механизм не входят.

## Поведение

| Событие | Результат |
|---|---|
| Штатный периодический запуск | Проверка разрешения, расчёт плана, отдельный допуск каждого действия |
| Masakari принимает аварийное событие | Сначала атомарная запись запрета, затем сохранение уведомления и отправка на восстановление |
| Сбой etcd, отсутствующее или повреждённое состояние | Новые автоматические операции не допускаются |
| Отказ guard при приёме аварии | Masakari не принимает/не ставит в очередь такое уведомление; требуется устранить существующую зависимость от координации и повторить обработку |
| Отказ guard для уже поставленного в очередь уведомления | Masakari engine переводит уведомление в `ERROR` до recovery и не оставляет его в `RUNNING` |
| Запрет установлен во время расчёта | План не запускается; следующий периодический цикл сможет повторить расчёт после разрешения |
| Запрет установлен между действиями | Следующее ещё не допущенное действие не вызывается; запрет не запускает отмену или обратную миграцию |
| Уведомление Masakari завершилось | Запрет сохраняется |
| Истёк любой таймаут / перезапущен сервис | Запрет сохраняется |
| Оператор разрешил работу | Новый номер поколения; старые планы остаются недопустимыми; следующий цикл рассчитывает новый план |
| Повторно пришло то же уведомление UUID | Повтор не снимает запрет и не блокирует заново после ручного разрешения |
| При разрешении одновременно возникла новая авария | Проверка ревизии отклоняет устаревшее разрешение либо новая авария устанавливает новый запрет |

Если запись запрета успешно завершилась, а следующий `notification.create()` или
вызов RPC для постановки уведомления в очередь завершился ошибкой, запрет и
маркер инцидента сохраняются. Ошибка API не означает, что восстановление было
поставлено в очередь. До recovery или `resume` оператор должен проверить общее
состояние и `reason`, запись уведомления в БД и фактическое наличие сообщения в
очереди. Автоматического компенсирующего снятия запрета в этом порядке API нет.

Допуск и установка запрета упорядочены транзакциями etcd. Граница гарантии — успешная транзакция допуска, а не момент получения запроса Nova. Между ними возможна задержка процесса или сети. Этот остаточный риск требует отдельного протокола координации уже начатых операций.

Полный машинно-читаемый состав, Git tree и SHA256 patch/wheel находится в [`manifest.json`](https://github.com/lebtmalorny-rgb/mimaric/blob/71b0123f390bfeaab4dc4ca2dffaa6fab32a6cdf/hotfixes/watcher-automation-hold/manifest.json). До сборки проверить локальный комплект и повторить каждый patch на новой копии точной базы:

```sh
python3 tools/watcher_automation_hold_delivery.py verify
python3 tools/watcher_automation_hold_delivery.py replay \
  --component watcher --source /path/to/exact/watcher-base \
  --output /tmp/watcher-hold-replay/watcher
```

Для остальных компонентов заменить `--component` на `masakari` или `kolla-ansible`. Инструмент сначала сравнивает исходный Git tree, отдельно делает `git apply --check` перед каждым patch, применяет их по порядку и сравнивает итоговый tree. Он не меняет исходный каталог, не обращается в сеть или облако и отказывается перезаписывать существующий output. Для Masakari перед replay уже должен быть применён prerequisite; для Kolla нужно сохранить четыре symlink из manifest. Локальный `etc/kolla/passwords.yml` не входит в индекс сравнения и комплект.

Общий пакет не опубликован в package index. В комплект входит только локальный wheel `powerops_watcher_guard-0.1.0-py3-none-any.whl`; его SHA256 проверяет та же команда. Воспроизводимая сборка из корня комплекта:

```sh
SOURCE_DATE_EPOCH=1789295229 python3.11 -m build --wheel --no-isolation \
  --outdir /tmp/watcher-hold-wheel packages/powerops-watcher-guard
```

Проверенная среда сборки: Python 3.11.15, `build` 1.6.1, setuptools 80.9.0. Две отдельные сборки дали одинаковый digest, указанный в manifest.

Из корня комплекта установить именно поставленный wheel в каждый из образов
`watcher_api`, `watcher_engine`, `watcher_applier`, `masakari_api` и
`masakari_engine` через фактическое Python-окружение сервиса версии 3.11 или
новее:

```sh
python3.11 -m pip install --no-deps --no-index \
  ./hotfixes/watcher-automation-hold/package/powerops_watcher_guard-0.1.0-py3-none-any.whl
python3.11 -m pip check
```

Эта команда не обращается к package index и не устанавливает зависимости. Она
применима только после того, как штатная сборка образа установила по действующим
constraints данного сервиса совместимые `requests>=2.25.1` и
`oslo.config>=9.0.0`; `pip check` должен завершиться без ошибок. Если сервис
работает не через команду `python3.11`, обе строки нужно выполнить тем же
интерпретатором его фактического Python-окружения версии не ниже 3.11.

Mistral, Nova и Ironic этим комплектом не изменяются. Изменения метрик Watcher и прежние экспериментальные PowerOps v2 в него не включены.

В Watcher добавляется внутреннее поле ActionPlan `automation_epoch`. UUID обозначает поколение периодического плана; `manual` — новый ручной/событийный план; NULL — исторический план без установленного происхождения. При включённом guard планы с NULL нужно пересчитать. Изменение типа исходного аудита не превращает уже помеченный периодический план в ручной. Поле не предоставляется для изменения через REST.

Смешанный состав старых и новых процессов при включённом guard не поддерживается. Для поставки на собственный форк Watcher сначала требуется проверить применение и совместимость его дополнительных изменений: локальные проверки этого комплекта относятся к указанному upstream commit.

## Порядок внедрения

Ни один из этих шагов не выполнялся на стенде при разработке.

1. Оставить балансировку выключенной и guard `enabled=false`. Зафиксировать отсутствие исполняемых автоматических планов и согласовать отдельное окно обновления сервисов.
2. Применить компонентные патчи к точным исходным базам. Установить локальный wheel во все образы Watcher API/engine/applier и Masakari API/engine до активации патченного кода. Зависимость нельзя получать из PyPI.
3. Установить патченный код во все эти образы. Для Watcher используются `watcher_api_image`/`watcher_api_tag`, `watcher_engine_image`/`watcher_engine_tag` и `watcher_applier_image`/`watcher_applier_tag`. Для Masakari нужны `powerops_masakari_api_image`/`powerops_masakari_api_tag` и `powerops_masakari_engine_image`/`powerops_masakari_engine_tag`. Отдельный API-образ обязателен: прежняя поставка PowerOps выбирала только изменённый engine.
4. При всё ещё выключенном guard выполнить миграцию Watcher до Alembic revision `a91c3f82d047` из патча:

   ```sh
   watcher-db-manage --config-file /etc/watcher/watcher.conf upgrade head
   watcher-db-manage --config-file /etc/watcher/watcher.conf version
   ```

   Это фактическая команда схемы из Watcher. Выполнить её один раз из патченного окружения с рабочим подключением к БД. После обновления ни один старый API/decision-engine/applier worker не должен оставаться активным при включении guard.
5. Подготовить одинаковый endpoint, namespace и параметры TLS во всех Watcher/Masakari конфигурациях. Состояние guard и маркеры уведомлений должны входить в резервирование etcd; их удаление, восстановление из старого snapshot или ручная подмена не являются способом возобновления работы.
6. До включения выполнить offline-проверки в каждой будущей реплике `watcher_api`, `watcher_engine`, `watcher_applier`, `masakari_api`, `masakari_engine`: импорт `powerops_watcher_guard`, версия distribution `0.1.0`, наличие патченного модуля соответствующего сервиса и читаемость каждого настроенного TLS-файла. Пример внутри каждого готового образа/контейнера без обращения к облаку:

   ```sh
   python3.11 -c "import importlib.metadata as m; import powerops_watcher_guard; assert m.version('powerops-watcher-guard') == '0.1.0'"
   test -r /etc/ssl/path/to/etcd-ca.pem
   test -r /etc/ssl/path/to/etcd-client.pem
   test -r /etc/ssl/path/to/etcd-client-key.pem
   ```

   Для Watcher также импортировать `watcher.common.automation_guard`, для Masakari — `masakari.powerops.watcher_automation`. Проверить все собранные image digest и все реплики. Допустимые TLS-корни: `/etc/pki/`, `/etc/ssl/`, `/var/lib/kolla/share/ca-certificates/`; parent traversal запрещён, cert/key задаются парой. Kolla проверяет синтаксис путей, но не наличие файлов. Пустой `ca_file` использует default trust store библиотеки `requests`, который не обязательно совпадает с системным trust store.
7. Явно инициализировать guard в состоянии BLOCKED при `watcher_automation_guard_enabled: "no"`, проверить одно состояние и revision через конфиги Watcher и Masakari, затем согласованно выставить `watcher_automation_guard_enabled: "yes"` во всех репликах. Общая precheck-роль импортирована ролями обоих сервисов и требует `enable_etcd=true`; отдельный guard endpoint допустим при сохранении этого существующего PowerOps prerequisite. Endpoint, который прошёл Kolla regex, всё равно может быть отклонён более строгой runtime-валидацией Gate, например userinfo или порт вне диапазона.
8. Все существующие здоровые планы с NULL/неизвестным происхождением и все старые периодические планы пересчитать. Проверить окончание Masakari recovery, состояние compute service/хоста/ВМ, а для каждой затронутой ВМ — отсутствие незавершённой или неопределённой Nova migration и `task_state`. Статус Watcher `SUCCEEDED` сам по себе недостаточен: при явном destination текущий `NovaHelper.live_migrate_instance` может вернуть успех после смены host до терминального статуса конкретной Nova migration. Получить актуальную revision только после ручного разбора уже допущенных действий и затем вручную разрешить работу. Периодические аудиты включать отдельным решением; доработка их не создаёт.

Не следует переиспользовать старые рекомендованные планы после включения или аварии. `resume` не запускает и не освобождает план автоматически. Следующий разрешённый периодический цикл должен собрать актуальную модель и рассчитать новый план. Пропущенные во время запрета тики не являются очередью миграций для последующего выполнения.

## Операторские команды

Команды выполняются в окружении с установленным общим пакетом и доступом к тому же etcd. Файл конфига берётся из фактически применённой сервисной конфигурации.

```sh
powerops-watcher-guard --config-file /etc/watcher/watcher.conf status
powerops-watcher-guard --config-file /etc/masakari/masakari.conf status

powerops-watcher-guard --config-file /etc/watcher/watcher.conf initialize \
  --actor operator-name --reason 'Первичное включение после проверки конфигурации'
```

`initialize` создаёт BLOCKED только при отсутствии состояния; повторная инициализация не должна сбрасывать существующее состояние.

После проверки восстановления повторно выполнить `status`, взять его числовую `revision` и передать её явно:

```sh
powerops-watcher-guard --config-file /etc/watcher/watcher.conf resume \
  --expected-revision 123 --actor operator-name \
  --reason 'Восстановление проверено, незавершённых операций нет' \
  --acknowledge-recovery
```

Число `123` — пример, его нельзя копировать вместо текущей ревизии. При конфликте ревизии снова проверить состояние и причину нового запрета. Автоматический повтор `resume` с новой ревизией без проверки оператора недопустим. Успешный `resume` не подтверждает исправность инфраструктуры сам по себе.

После `resume` снова выполнить `status` через оба сервисных конфига и убедиться, что совпадают `blocked=false`, новый `epoch` и `revision`. Старый epoch остаётся запрещённым. Затем дождаться следующего периодического audit и проверить, что создан новый план с новым epoch и актуальной моделью; старые планы не переводить в выполнение.

## Граница проверки

Локальная проверка охватывает SHA256, точные replay tree, импорт wheel вне editable source, CLI help/missing-state, отдельные процессы Watcher и Masakari с настоящим loopback etcd, исходные сервисные тесты с замоканными Nova/Ironic и рендер Kolla-конфигурации. Она не подтверждает фактический состав образов, настройки или поведение работающего облака. Проверка масштаба более 1000 хостов, нагрузочная оценка, реальная миграция/эвакуация, BMC fencing и production failover etcd здесь не выполнялись.

Текущий patch не вводит лимит в одну ВМ и не меняет штатную параллельность WeightPlanner/TaskFlow или настройку `max_workers`; их поведение под масштабной нагрузкой здесь не проверялось.

Отдельная защита плановых PowerOps/Mistral операций, включая самостоятельные миграции ВМ через Mistral/Nova, здесь не реализована. Будущий контракт должен поддерживать множество ВМ на разных хостах, но текущий guard не координирует такие операции с уже допущенными Watcher actions и допускает новые ручные Watcher plans. Никакого Mistral patch в этом комплекте нет; эту границу нельзя объявлять закрытой.
