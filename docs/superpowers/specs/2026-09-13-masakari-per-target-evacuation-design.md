# Эвакуации Masakari: последовательность по целевому compute

Дата: 2026-09-13. Статус: проект контракта для проверки перед реализацией.

Пользователь подтвердил отдельную поставку и сохранение автоматического выбора
назначения через Nova scheduler. Изменения исходников по этому проекту ещё не
выполнялись. Первый комплект Watcher уже опубликован отдельно в
`feature/watcher-automation-hold-2025.1`, commit
`c866d56fbf382afa4612c07039c34fbb5032aef5`.

## Проблема и результат

В Masakari 0809 при `powerops.enabled=true` все аварийные эвакуации используют
`powerops/evacuation/global`. Под блокировкой выполняются одна
`_evacuate_and_confirm` и `evacuation_interval`, исходно 5 секунд. ВМ в списке
может быть много, но разные назначения не могут восстанавливаться параллельно.

Цель: одновременно восстанавливать ВМ на разных целевых compute, сохраняя
строгую последовательность на каждом из них. Множество ВМ одного задания может
быть распределено по разным назначениям. Назначение по-прежнему выбирает Nova.

Предлагаемые исходные ограничения: одна активная эвакуация на целевой compute;
до трёх активных эвакуаций во всём контуре; пауза 5 секунд после успешного
завершения на том же compute. Общий предел и пауза настраиваются. Значение три —
консервативное предложение для первой версии, а не результат нагрузочного
измерения. Пауза снижает одновременность запуска, но не доказывает готовность
приложения или исчезновение стартовой нагрузки.

## Проверенные исходники и варианты

Masakari: точная база 0809, post-fence патч и опубликованный Watcher hold,
итоговый component commit `0c2fa56a36e71612e32bf50e174c465138d0c8fb`.
Его `masakari/compute/nova.py` использует Nova API 2.53; `target=None`
передаёт выбор назначения Nova. Общая блокировка находится в
`masakari/engine/drivers/taskflow/host_failure.py:433`.

Для Nova прочитаны официальные `stable/2025.1` файлы API evacuate, compute
manager, базовый virt driver и libvirt driver. HEAD скачанного полного checkout:
`ce37978276744e92d91251210a1d9c2784eea375`. Все четыре прочитанных снимка
побайтно совпали с файлами этого checkout; рабочее дерево чистое.
Состав работающего образа Nova ещё не проверен.

Рассмотрены три подхода:

1. **Допуск на принимающем nova-compute — выбранное направление.** Nova знает
   фактическое назначение до локального восстановления. Masakari сохраняет
   scheduler и передаёт несколько ВМ, Nova ограничивает исполнение на цели.
   Потребуются отдельные изменения Nova, Masakari и Kolla.
2. **Блокировка назначения только в Masakari.** Применима, когда назначение
   заранее задано, например reserved-host. Для автоматического назначения
   защита после появления `instance.host` уже опоздает. Пользователь выбрал
   сохранение автоматического scheduler.
3. **Эвакуация API 2.95, затем очередь start.** Само конечное состояние STOPPED
   недостаточно. В проверенном libvirt-пути compute manager вызывает
   `driver.spawn` без `power_on=False`, у libvirt исходно `power_on=True`,
   после spawn manager приводит ВМ к STOPPED. Поэтому этот вариант не даёт
   гарантии отсутствия раннего запуска гостя.

Источники: [Nova API history](https://docs.openstack.org/nova/2025.1/reference/api-microversion-history.html),
[compute manager](https://github.com/openstack/nova/blob/ce37978276744e92d91251210a1d9c2784eea375/nova/compute/manager.py),
[libvirt driver](https://github.com/openstack/nova/blob/ce37978276744e92d91251210a1d9c2784eea375/nova/virt/libvirt/driver.py).
Вывод о раннем запуске относится к прочитанному libvirt-пути, а не ко всем
гипервизорам. Одно изменение микроверсии в Masakari не является решением.

## Ответственность компонентов

**Masakari:** сохраняет fencing, подтверждённый Nova-down, блокировку исходного
хоста, VMove и существующие правила восстановления состояния ВМ. Вместо одной
глобальной последовательности подаёт ВМ через ограниченный пул. Ограничение
числа одновременно отправляемых запросов действует на процесс engine, а не
создаёт отдельный неограниченный пул для каждой аварии. Список ВМ обрабатывается
полностью, без лимита задания в одну ВМ. Ошибка прекращает новую подачу в рамках
затронутой recovery; уже отправленные операции наблюдаются до известного
результата либо сохраняются как неопределённые.

Перед запросом Nova сохраняется намерение с VM UUID, исходным хостом,
идентификатором попытки и отдельным global request ID. После появления Nova
migration UUID она связывается с той же попыткой. Request ID служит корреляции
и сам по себе не даёт права на допуск. Таймаут Masakari сохраняет неопределённое
намерение даже тогда, когда запрос ещё не дошёл до целевого compute. Такой
таймаут не означает отмены Nova и не разрешает слепой повтор evacuation.

**Nova:** scheduler, Placement и проверка пригодности назначения работают
штатно. Ограничитель находится на принимающем compute, на пути
`rebuild_instance(recreate=True)`, до локальных операций восстановления и
`driver.spawn`. Он охватывает всю эвакуацию, включая первый запуск гостя,
обработку результата и паузу. Его освобождение не зависит от раннего
`VMove.SUCCEEDED` или одной смены `instance.host` в Masakari. Ограничитель
применяется ко всем эвакуациям на включённом compute; обычные build/start и
live migration этим отдельным патчем не включаются в общую очередь.

**Общее хранилище допуска:** отдельный namespace etcd для записей эвакуаций,
целевых compute и общего лимита. Состояние не использует глобальный epoch
Watcher и не снимает аварийный Watcher hold. Компонент содержит только протокол
допуска и операторское чтение/разбор зависших записей; отдельный daemon не нужен.

**Kolla:** выключенный по умолчанию режим, единые настройки, пакет в нужных
образах и проверяемая последовательность включения. Нужны патченные Masakari
engine и Nova compute на всех возможных назначениях. Kolla не исполняет
эвакуации и не снимает блокировки автоматически.

## Контракт допуска и отказов

Запись операции содержит UUID ВМ, UUID Nova migration, UUID целевого compute,
идентификатор попытки/владельца, состояние и ревизию. Ключ цели использует
глобально однозначный compute/provider UUID, а не неоднозначное короткое имя.
Состояния различают отправку запроса, ожидание допуска, исполнение, паузу,
подтверждённое завершение, отказ до допуска и неопределённый результат.

1. До первого локального эффекта Nova регистрирует операцию. Допуск атомарно
   занимает место на конкретном compute и одно место общего лимита. Нельзя
   удерживать один из этих ресурсов, бесконечно ожидая второй.
2. Пока цель занята, следующий запрос остаётся ожидающим и не вызывает
   восстановление, spawn или повторную эвакуацию на другое назначение.
   Количество одновременно поданных запросов ограничено Masakari. Ожидание
   на стороне Nova имеет отдельный лимит; его истечение до допуска запрещает
   исполнение этого запроса. Это не таймаут наблюдения Masakari: запрос с
   неизвестным результатом наблюдения может продолжать выполняться в Nova и
   должен оставаться учтённым.
3. Повторная доставка одной migration UUID не получает второй допуск. Даже
   совпадение migration UUID не даёт другому процессу право продолжить чужую
   активную попытку. Все переходы сравнивают владельца и ревизию.
4. После успешного завершения Nova операция проходит паузу, затем освобождает
   цель и общий слот. Подтверждение включает нормальный выход всего Nova
   rebuild/evacuation пути, завершённую migration и согласованное состояние
   ВМ. HTTP-ответ Masakari или одиночное наблюдение ACTIVE этого не заменяют.
5. Потеря процесса, неоднозначный ответ etcd или ошибка после допуска не
   освобождают запись по TTL. Неопределённая операция продолжает занимать
   соответствующий слот; другие свободные цели могут использовать оставшиеся
   места общего лимита. После исчерпания лимита новые эвакуации ждут.
6. После рестарта нельзя начать следующую ВМ просто потому, что исчез локальный
   semaphore. Завершённую операцию можно довести через новую полную паузу;
   активная/неопределённая требует разбора. Перевод часов не должен сокращать
   паузу: в процессе используется монотонное ожидание, после рестарта — новая
   полная пауза для уже доказанно завершённого действия.
7. Операторское освобождение неопределённой записи требует точной ревизии,
   подтверждения результата Nova и отсутствия процесса/доставки, способных
   позднее продолжить старую попытку. При невозможности это доказать запись
   сохраняется. Автоматическое освобождение на основании таймаута запрещено.

Новая очередь не отменяет и не разворачивает уже начатые эвакуации. Порядок
допуска на одной цели сериализован; строгая FIFO-справедливость между разными
авариями не является гарантией первой версии.

## Границы поставки

Комплект публикуется отдельной веткой поверх уже опубликованного Watcher hold.
Сам Watcher hold, его API, schema и пакет не изменяются. Компонентные изменения
Masakari, Nova и Kolla оформляются отдельно с точными исходными SHA, patch order,
контрольными суммами и инструкцией совместного включения.

Сохраняется существующая семантика Nova API 2.53 для запросов Masakari:
изменение очереди не должно попутно менять требуемое конечное состояние ВМ.
Не изменяются Nova `max_concurrent_builds`, лимиты live migration, Ironic power
операции и Nova scheduler/Placement policy.

Смешанная работа старых и новых Nova compute при включённом режиме не
поддерживается. Перед включением проверяются все образы и реплики, версия
пакета, доступ к одному namespace и отсутствие старых неопределённых действий.
Конфигурации достаточно только после проверки, что код действительно присутствует.

Защита плановых Mistral миграций/выключений и обычных start/build — следующий
отдельный контракт. Этот патч не объявляется общей защитой всех операций
на хосте или гарантией отсутствия перегрузки хранилища. Прямые операции BMC и
гипервизора также вне его гарантии.

## Проверка реализации

- Много ВМ одного задания: все получают отдельные записи, ни одна не теряется.
- Два Nova процесса/две recovery на одном compute: одновременно не более одного
  вызова пути восстановления; пауза также исключает новый допуск.
- Разные compute: восстановление действительно пересекается по времени при
  наличии общего бюджета; общий предел соблюдается между процессами.
- Nova автоматически выбирает одинаковую либо разные цели: защита появляется
  до первого локального восстановления/запуска, назначения не захардкожены.
- Реальный Nova manager до границы virt driver, с подменой только внешних
  сервисов и драйвера: проверяется порядок допуска, spawn, результата, паузы.
- Повтор RPC, потеря ответа, падение после допуска, рестарт, истечение ожидания,
  старое завершение и конфликт операторской ревизии не дают второй эффект.
- Отдельные процессы с настоящим локальным etcd доказывают общий допуск и
  сохранение записи после рестарта; mock semaphore этой проверки не заменяет.
- Старый выключенный режим, fencing/Post-fence и сохранение прежнего состояния
  ВМ проходят регрессионные проверки; отказ одной recovery не отменяет чужую.
- Kolla рендерит согласованные настройки и проверяет prerequisites; replay всех
  компонентных патчей даёт точные итоговые деревья и неизменные исключённые файлы.

Проверки исходников и локальные тесты не подтверждают фактическую готовность
облака на 1000+ хостов. Нагрузочный прогон, живые миграции/эвакуации, deploy,
перезапуск сервисов и BMC операции данным проектированием не выполняются.
