# PowerOps: автоматический плановый возврат и ручной аварийный возврат

Дата: 2026-09-05.
Статус: пять пользовательских сценариев и состав доработок согласованы
2026-09-05, включая hook Masakari и отдельный compatibility-патч Nova.
Спецификация принята для подготовки плана; код ещё не изменён.

## 1. Цель и границы

После отдельного запуска плановой операции весь её штатный путь выполняется
без ручного resume. Выключение не запускает последующее включение само.
Возврат после аварийного восстановления Masakari остаётся ручным.

| Сценарий | Поведение |
| --- | --- |
| Выключение без ВМ | `require_empty`: любая ВМ на хосте, включая `SHUTOFF`, запрещает выключение |
| Выключение с остановкой ВМ | `stop`: остановить только исходные `ACTIVE`, сохранить их UUID, проверить все оставшиеся ВМ перед выключением |
| Выключение с миграцией | `live_migrate`: последовательно мигрировать исходные `ACTIVE`, выключить только после подтверждения пустого хоста |
| Включение без запуска ВМ | Включить хост по актуальной записи планового выключения; после проверок вернуть его в работу |
| Включение с запуском ВМ | Включить хост и последовательно запустить только ВМ, остановленные связанной плановой операцией |

Исходные `SHUTOFF` остаются остановленными. Мигрировавшие ВМ не возвращаются
обратно. После `stop`, который не остановил ни одной ВМ, список запуска пуст,
хотя на хосте могут оставаться исходные `SHUTOFF`.

Не добавляются scheduled power-on, плановая evacuation, автоматическая очистка
libvirt, автоматический аварийный возврат и глобальное изменение обработки
исключений сторонних библиотек. Ironic остаётся power-only: `manageable`,
`network_interface=noop`, без provisioning/cleaning/inspection.

## 2. Проверенная исходная реализация

Mistral: `fix/powerops-masakari-v1-uuid`, `7be711a`.
Delivery baseline: `b798376`, пять hotfix-патчей сохранены без изменений.

- `mistral/actions/powerops/planned.py`: off и reboot уже реализованы;
  reboot запускает остановленные им ВМ без ручной паузы.
- `mistral/actions/powerops/clients.py`: операции над ВМ последовательные,
  с ожиданием, pacing и проверкой принадлежности restart manifest хосту.
- `etc/mistral/power_ops.yaml`: off возвращает `stopped_instance_ids`,
  отдельный return принимает список от вызывающего и всегда проходит паузу.
- `mistral/actions/powerops/return_host.py`: Boolean
  `stale_domains_checked=True` проверяется, но серверное доказательство
  прохождения паузы ещё не требуется.
- `mistral/services/powerops.py`, `mistral/engine/actions.py`: общий RBAC
  и передача trusted resume context уже имеют точки расширения.
- Masakari `masakari/engine/drivers/taskflow/driver.py`: общий host lock
  охватывает host-failure flow. История завершённых владений lock не хранится.
- Masakari `masakari/engine/manager.py`: maintenance меняется ещё до вызова
  TaskFlow driver; одного hook непосредственно в fence task недостаточно.

Эти наблюдения получены из локальных исходников, не из работающих контейнеров.

## 3. Варианты и выбранный проект

1. **Одноразовая серверная запись цикла плюс аварийный запрет в общем etcd**
   — рекомендуемый вариант. Запись связывает off/on и manifest, атомарное
   получение права на возврат исключает два независимых запуска по одной
   записи. Masakari может запретить автоматический возврат при аварии.
2. Только читать старый `SUCCESS` execution из Mistral — меньше изменений,
   но история Mistral сама по себе не доказывает отсутствие последующей
   аварии и не обеспечивает одноразовое использование. Вариант отклонён.
3. Отдельный сервис учёта и агент проверки гипервизора — более широкая
   автоматизация, но новый сервис/доступ к хостам не нужен для выбранного
   планового пути и не входит в эту итерацию.

Согласованная зависимость: вариант 1 требует небольшого дополнительного патча
Masakari и opt-in настройки Kolla, а не только изменения Mistral.
Fencing/evacuation алгоритм и порядок его задач не меняются.

## 4. Публичный контракт workflow

Существующие три политики `power_ops.planned_power_off` и
`power_ops.planned_reboot` сохраняются. Старые output keys не удаляются.

Новый workflow `power_ops.planned_power_on` принимает только `host` и
`segment_uuid`. Точный source execution, Ironic UUID и список запуска он
получает из текущей серверной записи хоста. Пользователь не копирует список
ВМ и не выбирает историческую запись. Входные `stopped_instance_ids`,
`planned=true`, receipt state и поля авторизации для этого workflow запрещены.

Новый output содержит `host`, `operation`, `source_execution_id`,
`cycle_id`, фактические итоговые состояния сервисов и UUID ВМ, которые
обрабатывались для запуска. Пустой manifest не означает ошибку.

`power_ops.power_on_and_return` сохраняет ручную паузу как аварийный/ремонтный
путь. Его контракт усиливается trusted resume validation: авторизованный
resume реального paused execution на ожидаемой задаче; серверная запись
связана с execution/task и не создаётся из пользовательского env.
Прямой вызов return action с одним `stale_domains_checked=True` не обходит gate.
Флаг остаётся заявлением оператора о проверке, не доказательством физического
состояния гипервизора. Ручной аварийный возврат не запускает эвакуированные ВМ
на исходном хосте; при аварийном запрете restart manifest должен быть пустым.

## 5. Серверная запись планового цикла

Авторитетная текущая запись хранится под
`powerops/return/v1/hosts/<canonical-host>` в уже используемом общем etcd.
Она не прикрепляется к lease процесса: рестарт executor не должен удалять
знание о незавершённой операции. Вывод execution используется для аудита,
но не для восстановления права на автоматический возврат.

Поля: версия протокола, случайный `cycle_id`, host/segment/Ironic UUID,
project ID, исходные workflow/action execution IDs, policy, исходный набор
ВМ со статусами и размещением, подтверждённый список остановленных ВМ,
признак применения hard-off, состояние цикла, action ID владельца возврата.
Пароли, токены, BMC credentials в запись и в ошибки не помещаются.

Состояния:

```text
PREPARING -> OFF_READY -> RETURNING -> RETURNED
     \           \           \
      +-----------+-----------+----> MANUAL_REQUIRED
```

- Новое плановое выключение создаёт `PREPARING` до первой мутации,
  под host lock. Текущий незавершённый цикл нельзя затереть новым.
  При включённой новой функции исходный хост должен быть stable-on,
  Nova enabled/up, maintenance=false и без аварийного запрета. Нельзя
  оформить уже неизвестно кем выключенный хост как новое плановое выключение.
- По мере остановки ВМ подтверждённые результаты записываются для диагностики
  частичного выполнения. При сбое такая запись не становится `OFF_READY`.
- `OFF_READY` записывается только после всех проверок ВМ и stable power-off.
  Для включения дополнительно нужен успешный исходный execution Mistral;
  ручная установка `SUCCESS` без соответствующей серверной записи не помогает.
  Подтверждённое применение hard-off вместо этого оставляет `MANUAL_REQUIRED`.
- Перед первой мутацией включения `OFF_READY` атомарно меняется на `RETURNING`,
  привязанный к текущему action execution. Второй вызов не получает это право.
- `RETURNED` записывается после подтверждённого старта manifest и возврата
  сервисов. Старый цикл никогда повторно не переводится в `OFF_READY`.
- Ошибка/таймаут после получения права на мутацию требует диагностики;
  автоматический перезапуск всей последовательности не выполняется.
  Зависшая запись `PREPARING/RETURNING` также запрещает новый авто-цикл.

Ручной путь инвалидирует старую запись до первой команды питания.
`planned_reboot` остаётся одной непрерывной операцией под host lock: при
opt-in он использует `PREPARING -> RETURNED`, не публикуя `OFF_READY` для
отдельного включения. Его частичный сбой требует ручного восстановления.

Изменения записи используют etcd transaction: сравнение актуальной revision
записи и владельца host lock. Для чтения не применяются потенциально устаревшие
member-local reads. Lease-lock и постоянная запись имеют разные назначения.
Семантика основана на [etcd API](https://etcd.io/docs/v3.6/learning/api/).

Удаление/потеря записи не разрешает автоматический возврат. Восстановление etcd
из backup требует выключить новую автоматику и провести ручную сверку:
старый snapshot может восстановить ранее использованную запись.

## 6. Аварийный запрет и межсервисная граница

Отдельный постоянный ключ `powerops/return/v1/emergencies/<canonical-host>`
содержит запрет возврата и ID принятой host-failure notification.
Masakari публикует запрет после определения реального host-failure события,
до изменения maintenance и до ожидания host lock. Невалидные/игнорируемые
события и обычный `STARTED` не создают разрешение или запрет возврата.
Driver дополнительно проверяет наличие запрета до запуска recovery flow,
чтобы прямой вызов driver не обходил этот контракт.

При невозможности подтвердить запись запрета recovery не переходит к новым
опасным мутациям; ошибка явно отражается в notification. Это выбранное
fail-closed поведение, а не обещание доступности recovery при потере etcd.

Mistral проверяет отсутствие аварийного запрета при начале плановой операции,
при атомарном получении права на возврат и перед дальнейшими внешними
мутациями штатного автоматического пути. Новый запрет во время операции
прекращает дальнейшее выполнение. Защитные disable/maintenance=true
не запрещаются самим аварийным ключом, но всё ещё требуют владения host lock.
Проверка не отменяет уже отправленный API-запрос; это ограничение явно остаётся.

Завершение evacuation, исчезновение notification из API и истечение времени
не снимают запрет. Только успешный доверенный ручной возврат может очистить
именно проверенную revision запрета под host lock; более новая авария не
должна быть затёрта. При этом старый плановый cycle инвалидируется, а новый
разрешается только после завершения ручного возврата.

Все пути чтения/записи общего протокола имеют одинаковые contract fixtures
в Mistral и Masakari. Протокол не защищает от администратора с прямым доступом
к etcd, BMC/libvirt или внешних power actions, обходящих PowerOps.

## 7. Проверки и последовательность планового включения

До команды питания, под host lock:

1. RBAC, opt-in функции, точный host/segment/Ironic UUID и project scope.
2. Актуальный `OFF_READY`, успешный source execution, отсутствие аварийного
   запрета и незавершённого конкурирующего цикла.
3. Stable-off без conflicting target/last_error; Nova disabled и Masakari
   maintenance=true. Уже включённый неизвестным путём хост не принимается
   как доказательство успешного планового возврата.
4. Повторная сверка VM inventory: после empty/migration хост пуст; после stop
   UUID/размещение соответствуют записи и состояния допустимы. Чужие/новые,
   исчезнувшие или перемещённые ВМ дают отказ до power-on.

Затем: атомарный claim -> power-on -> stable-on -> свежий heartbeat Nova
после начала включения при сохранённом disabled -> повторная сверка ВМ ->
последовательный start собственного manifest с ожиданием ACTIVE и pacing ->
Nova enabled -> maintenance=false -> `RETURNED`.

Неожиданно `ACTIVE` до управляемого старта ВМ, которая должна оставаться
остановленной, означает расхождение и ручную диагностику, не молчаливый успех.
Внутри подтверждённого текущего старта `ACTIVE` является ожидаемым результатом.
Применённый hard-off или неподтверждённый тип выключения не разрешает новый
автоматический return: это ручной путь. `allow_hard_off` не отменяет проверок.

Ready здесь означает перечисленные наблюдения API, а не полную диагностику
ОС, storage, OVS/OVN и libvirt. Не добавляется ложный автоматический
`stale_domains_checked=true`. Приёмка на стенде должна отдельно подтвердить
работоспособность compute/storage/network после загрузки.

## 8. Ошибки, повторы и остаточные ограничения

- После первой мутации ошибка запускает попытки сохранить maintenance и
  Nova disabled. Утрата lock или недоступность API может не позволить это;
  исходная ошибка сохраняется, частичный результат доступен для диагностики.
- Частичная остановка/миграция/запуск не откатывается автоматически. Уже
  выполненные действия над ВМ не отменяются лишь из-за `ERROR` execution.
- Повторный request/duplicate delivery не запускает второй цикл. Для
  `RETURNING` без доказанного завершения результат считается неопределённым.
  После `504` сначала ищется существующий execution; новый не создаётся вслепую.
- Timeout одной API-мутации не означает, что она не произошла. Следующий
  независимый шаг не выполняется по предположению об исходе запроса.
- etcd revision защищает записи etcd, но не превращает Nova/Ironic/Masakari
  в одну транзакцию. Уже отправленную команду питания нельзя отозвать проверкой
  lock. Внешние администраторы могут менять ВМ вне PowerOps lock.
- Пустой список ресурсов при недостаточных правах не считается доказанным
  отсутствием ВМ. Права и видимость всех проектов проверяются при приёмке
  служебных credentials внутри executor, а не только admin CLI.

## 9. Разделение патчей и rollout

1. Mistral: серверная запись, planned on, согласованный manifest и trusted
   ручной resume; покрыть engine/API/action обходы и совместимость reboot.
2. Masakari: публикация/проверка аварийного запрета, без перестановки существующих
   fencing/evacuation задач.
3. Kolla-Ansible: отдельный opt-in `powerops_planned_return_enabled: "no"`,
   рендер `[powerops] planned_return_enabled=false` по умолчанию в Mistral
   и Masakari, reconciliation нового workflow и preflight протокола.
   Существующий `enable_powerops` не должен молча включать новую функцию.
   При выключенном opt-in новый planned on отклоняется до любой мутации;
   новые автоматические циклы не создаются. Существующие аварийные запреты
   не очищаются переключением настройки.
4. Delivery: обновить три устаревшие структурные проверки из WORKFLOW-AUDIT,
   инструкции, набор патчей и SHA256SUMS; не переписывать hotfix 0001–0005.

Перед включением opt-in требуется обновить все участвующие Mistral и Masakari
реплики, проверить общий namespace etcd и версию протокола. Смешанные старые/
новые реплики не поддерживаются для автоматики; один config flag не доказывает
готовность реплик. Старые выключения без новой записи включаются вручную.

Подготовка изменений выполняется локально. Образы собирает и переносит
пользователь; deploy/reconfigure, рестарты и реальные power actions не входят
в разрешение на разработку. При rollback сначала выключается opt-in;
записи циклов и аварийные запреты не удаляются для обхода отказа.

Отдельным совместимым патчем в эту серию включается передача host/binary
в Nova disable/enable: подтвердить тестами ветви SDK с API <2.53 и >=2.53,
не меняя глобальную microversion. В установленном SDK 4.10.0 legacy методы
не подставляют эти поля из service автоматически. Современная ветвь использует
service ID. Обе ветви должны сохранить read-back и deadline.

Host status остаётся доступным без обязательного подключения к etcd; это
наблюдение, а не разрешение power action. Сообщения сторонних исключений
проверяются отдельно; глобальная переделка исключений Mistral не входит в серию.

## 10. Критерии локальной проверки

- Все пять сценариев: пустой/непустой хост, исходные SHUTOFF, последовательность
  stop/migrate/start, ожидания, pacing, отсутствующая обратная миграция.
- Расхождения UUID/host/segment/project и VM inventory до/после включения;
  неизвестные состояния, новые ВМ, повреждённый/подменённый manifest.
- Повторный source, два включения, duplicate delivery, рестарт executor,
  смена revision, потеря записи/lock, неопределённый ответ после записи.
- Авария до off, между off/on, во время RETURNING и во время ручного resume;
  новый аварийный запрет не стирается завершением старого возврата.
- Отказ записи аварийного запрета не допускает дальнейший recovery;
  ignored/STARTED notifications не включают хост и не снимают запрет.
- API/engine/action авторизация, невозможность обойти ручной gate через
  прямой action, env, update state или task rerun.
- Реальный парсер workbook и engine переходы; HTTP-intercept тесты SDK,
  сверка обеих реализаций etcd protocol, тесты deadline/partial mutations.
- Сохранение тестов пяти hotfix-патчей; актуализированные cross-repository и
  delivery checks, apply/reverse-check серии на чистой базе.

Зелёные mock/unit/contract tests не являются runtime-приёмкой. Стендовая
приёмка отдельно проверяет images/entry points, TLS/RBAC, etcd, BMC, миграцию,
heartbeat и реальные ВМ. Реализация выполняется по отдельному плану с
проверками и review между законченными патчами.
