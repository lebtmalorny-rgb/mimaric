# Требования к окружению перед развёртыванием кластера

Для **Kolla-Ansible PVS 1.0.0**. Документ определяет требования к именам узлов, DNS и сетевой доступности VIP/API/Horizon. Имена, адреса и домен в примерах необходимо заменить значениями целевого окружения.

## 1. Готовность серверов и сети

- На серверах установлена ОС, поддерживаемая выбранной поставкой кластера.
- Для каждого сервера выделены постоянные IP, определены роли, интерфейсы, VLAN, подсети и шлюзы.
- Машина установки имеет SSH-доступ ко всем целевым серверам и права повышения привилегий до `root`.
- Узлы имеют доступ к согласованным DNS- и NTP-серверам; системное время синхронизировано.
- Доступны необходимые репозитории пакетов, реестр контейнерных образов и используемые внешние сервисы.
- Межсетевые экраны разрешают соединения между компонентами согласно выбранной схеме. Из пользовательской сети разрешён доступ к Horizon по TCP/443 при HTTPS или TCP/80 при HTTP.

## 2. Имена узлов

Каждый узел должен иметь уникальное и постоянное короткое имя и полное доменное имя — FQDN. Имена согласуются с inventory до развёртывания.

| Назначение | Короткое имя | FQDN | IP на API-интерфейсе |
|---|---|---|---|
| Контроллер 1 | `ctrl01` | `ctrl01.cloud.example.test` | `10.10.10.11` |
| Контроллер 2 | `ctrl02` | `ctrl02.cloud.example.test` | `10.10.10.12` |
| Контроллер 3 | `ctrl03` | `ctrl03.cloud.example.test` | `10.10.10.13` |
| Compute | `compute01` | `compute01.cloud.example.test` | `10.10.10.21` |

Короткие и полные имена узлов должны разрешаться в согласованные API-адреса. Для коротких имён требуется поисковый домен DNS либо соответствующие записи `/etc/hosts`.

**Обязательное условие RabbitMQ:** короткое имя каждого узла RabbitMQ однозначно разрешается в его собственный IP на `api_interface`. Недопустимы конфликтующие соответствия этому имени: `127.0.0.1`, `127.0.1.1`, VIP или адрес другого интерфейса.

При отдельной сети управления SSH-адрес может отличаться от API-адреса; он фиксируется в inventory через `ansible_host`.

## 3. DNS и сервисные имена

До развёртывания должны быть созданы DNS-записи для узлов и сервисных точек доступа. Сервисные имена указывают на VIP кластера.

| Сервисное имя, пример | Назначение | На какой адрес указывает |
|---|---|---|
| `api-int.cloud.example.test` | Внутренние API | `kolla_internal_vip_address` |
| `cloud.example.test` | Horizon и внешние API | `kolla_external_vip_address` |

Эти имена передаются команде развёртывания как `kolla_internal_fqdn` и `kolla_external_fqdn`. Если используется отдельное имя Horizon, оно также должно указывать на внешний VIP и быть согласовано как `horizon_external_fqdn`.

| Откуда выполняется обращение | Что должно разрешаться |
|---|---|
| Машина установки | Имена, используемые для SSH, API и внешних зависимостей |
| Узлы и сервисные контейнеры | Имена соседних узлов, используемых API и зависимостей |
| Рабочие компьютеры пользователей | Имя Horizon и других используемых внешних endpoints |

Для небольшого стенда допустим `/etc/hosts`, если нужные записи согласованно присутствуют на всех потребителях. Записи только на машине установки недостаточны. DNS должен быть доступен независимо от развёртываемого кластера.

При HTTPS сертификат должен содержать используемое сервисное DNS-имя в SAN, а клиенты должны доверять его центру сертификации.

## 4. Требования к VIP и отказоустойчивости

Выбирается один механизм обслуживания VIP: **Keepalived** или **FRR**. Для одного VIP они не должны работать одновременно. Адреса резервируются, исключаются из DHCP-пулов и не используются другими устройствами.

Балансировщики размещаются на узлах группы `loadbalancer`; в штатном inventory эта группа наследует `network`. Размещение должно быть заранее согласовано.

| Требование | Keepalived | FRR / BGP в данной поставке |
|---|---|---|
| Размещение VIP | На активном балансировщике | На `dummy0` здоровых балансировщиков |
| Адресный план | VIP из соответствующих подключённых подсетей балансировщиков | IPv4 VIP, анонсируемые как маршруты `/32` |
| Сеть | Общие L2-сегменты между балансировщиками для соответствующих VIP | Доступные BGP-соседи и согласованная маршрутизация к VIP |
| Сетевые разрешения | VRRP — IP protocol 112; прохождение ARP | BGP — TCP/179 между соседями |
| Дополнительные условия | VRID отличается от других VRRP-кластеров в том же сегменте | Согласованы ASN, адреса соседей и политики приёма/анонса; на балансировщиках доступен модуль `dummy` |

**Для FRR:** маршруты к внутреннему VIP должны обеспечивать доступ от всех нужных узлов, включая control/compute/storage и машину установки; к внешнему VIP — из пользовательских сетей. Учитывается обратная связность. По умолчанию BGP между балансировщиками не обеспечивает маршруты для остальных машин: требуется подготовка сетевой инфраструктуры.

Для маршрутизируемой схемы FRR рекомендуется выделять VIP вне подключённых подсетей клиентов и узлов. Если VIP находится в их подсети, отдельно согласуется доставка трафика, чтобы обращение не зависело от случайного ARP-ответа.

## 5. Адрес доступа к Horizon

**Для Keepalived и FRR пользователи обращаются к имени Horizon, которое разрешается во внешний VIP.** Способ отказоустойчивости не меняет назначение этого адреса.

- URL: `https://cloud.example.test` при TLS или `http://cloud.example.test` при HTTP.
- По умолчанию имя Horizon совпадает с `kolla_external_fqdn`.
- Внешний VIP может быть частным адресом корпоративной сети.
- При общей внутренней и внешней точке доступа допускается один VIP/FQDN с согласованными параметрами TLS.

## 6. Что передать команде развёртывания

- Таблицу узлов: роли, hostname, FQDN, SSH- и API-адреса, интерфейсы, VLAN, подсети и шлюзы.
- Адреса DNS/NTP, поисковый домен и подтверждение разрешения коротких и полных имён.
- Внутренний и внешний VIP, сервисные FQDN и имя Horizon.
- Выбранный механизм HA: для Keepalived — VRID и L2-схему; для FRR — ASN, BGP-соседей и схему маршрутизации VIP.
- Подтверждение SSH-доступа и необходимых сетевых разрешений; сертификаты и цепочку CA при TLS.

**Критерий готовности:** адресный план согласован, имена разрешаются в правильные IP, доступ к узлам проверен, сеть подготовлена для выбранного механизма VIP. До деплоя сами VIP и Horizon могут не отвечать; их фактическая доступность и переключение при отказе проверяются после развёртывания.

Основание: переменные PVS (`kolla-ansible-pvs_1.0.0/ansible/group_vars/all.yml`), проверка RabbitMQ (`kolla-ansible-pvs_1.0.0/ansible/roles/rabbitmq/tasks/precheck.yml`), Keepalived (`kolla-ansible-pvs_1.0.0/ansible/roles/loadbalancer/templates/keepalived/keepalived.conf.j2`), FRR (`kolla-ansible-pvs_1.0.0/ansible/roles/loadbalancer/templates/frr/frr.conf.j2`). Документ проверен по исходникам; готовность целевого окружения не проверялась.
