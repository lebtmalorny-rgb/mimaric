# OpenStack Epoxy 2025.1: парольная политика без LDAP

Дата проверки источников: 17 сентября 2026 года.

## 1. Краткий вывод и границы решения

Пользователи хранятся в SQL backend Keystone; вход выполняется через Horizon или Identity API v3. Требования к человеческим учётным записям:

- пароль не короче 8 символов, доступный алфавит не менее 70 символов;
- обязательная смена пароля, установленного администратором, до получения доступа;
- блокировка после 4 неправильных паролей;
- разблокировка администратором либо автоматически через заданный интервал.

**Сервисные записи полностью исключаются из этих требований, включая длину и сложность пароля.** Исключение означает отсутствие соответствующей проверки, а не необходимость назначать слабые пароли. Допустимые типы данных, технические ограничения длины и правила отключения парольной аутентификации остаются частью API.

Обязательная смена, блокировка и индивидуальные исключения из этих двух механизмов есть в штатном Keystone. **Индивидуального исключения из `password_regex` в Keystone 2025.1 нет. Поэтому полное решение с указанным разграничением требует доработки Keystone и подготовки сервисных пользователей в автоматизации Kolla-Ansible.** Одних файлов конфигурации недостаточно.

Патчи Keystone и Kolla-Ansible подготовлены в [password-policy-patches](https://github.com/lebtmalorny-rgb/mimaric/blob/60bbc29354ee852cf70bed835235344a205f3468/README.md), вместе с исходным архивом для сборки и отчётами локальных проверок. Собранный контейнерный образ и применение на кластере не выполнялись. `password_policy_exempt` — расширение этого патча; vanilla Keystone его не поддерживает.

Основание: [штатные механизмы Keystone](https://docs.openstack.org/keystone/2025.1/admin/configuration.html#security-compliance-and-pci-dss), [реестр пользовательских исключений](https://docs.openstack.org/keystone/2025.1/admin/resource-options.html), [общий валидатор](https://docs.openstack.org/keystone/2025.1/_modules/keystone/common/validation/validators.html#validate_password).

## 2. Где что настраивается

| Компонент | Место | Назначение |
|---|---|---|
| Keystone | `/etc/kolla/config/keystone.conf` на deploy-узле | Парольный regex, первая смена, 4 ошибки, длительность блокировки |
| Horizon | `/etc/kolla/config/horizon/_9999-custom-settings.py` | Форма смены истёкшего/временного пароля; отсутствие общей проверки сложности в UI |
| Пользователь Keystone | `user.options` через Identity API | Индивидуальная классификация и исключения |
| Исходники Keystone | Собственный проверенный образ на базе используемой версии 2025.1 | Проверка политики с учётом целевого пользователя |
| Kolla-Ansible | Подготовка пользователей перед назначением пароля в `service-ks-register` и других местах регистрации | Исключения с момента создания, включая новые сервисы |
| Kolla-Ansible | `/etc/kolla/globals.yml` | Выбор собственного образа Keystone |

Пути предполагают `node_custom_config: /etc/kolla/config`. Их нужно адаптировать при другом значении. Не редактировать генерируемый `/etc/kolla/keystone/keystone.conf` на контроллере вместо исходного override.

Пути проверены в локальных задачах Keystone (`kolla-ansible-pvs_1.0.0/ansible/roles/keystone/tasks/config.yml` в исходном архиве Kolla) и задачах Horizon (`kolla-ansible-pvs_1.0.0/ansible/roles/horizon/tasks/config.yml` в исходном архиве Kolla). Общий механизм: [Kolla configuration overrides](https://docs.openstack.org/kolla-ansible/2025.1/admin/advanced-configuration.html#openstack-service-configuration-in-kolla).

## 3. Инвентаризация до включения политики

На deploy-узле с административной OpenStack-сессией:

```bash
openstack domain list
openstack user list --long
openstack role assignment list --names
openstack user show <USER_ID> -f json
```

Составить явный реестр: UUID, domain ID, имя, назначение, владелец, человек/сервис. Проверить сервисы Nova, Neutron, Glance, Cinder, Placement и все реально включённые компоненты, а также deploy-автоматизацию, мониторинг и задания резервного копирования.

Роль `service`, имя `nova`, принадлежность проекту `service` и наличие `admin` не являются достаточным автоматическим критерием. Исключение относится к целевой учётной записи, а не к роли выполняющего запрос администратора. Человеческие администраторы также подчиняются политике. Не следует использовать одну запись одновременно для человека и автоматизации.

Зафиксировать версии пакетов/образов, текущие overrides, существующие `user.options`, `password_expires_at`, настройки Horizon. Получить список мест создания сервисных пользователей: общей роли `service-ks-register` может быть недостаточно, например для bootstrap или специальных сервисных доменов.

## 4. Настройки Keystone для человеческих пользователей

Целевой фрагмент `/etc/kolla/config/keystone.conf` — включать после выполнения разделов 5–7:

```ini
[security_compliance]
password_regex = ^[!-~]{8,}\Z
password_regex_description = Use at least 8 printable ASCII characters without spaces.
change_password_upon_first_use = true
unique_last_password_count = 1
minimum_password_age = 0
lockout_failure_attempts = 4
lockout_duration = 900
```

Значение `900` — пример: 15 минут. Администратор выбирает требуемый интервал в секундах. Для блокировки до ручного снятия удалить `lockout_duration` из всех применяемых overrides, чтобы использовалось штатное значение `None`; не записывать в INI строку `None`.

`[!-~]` содержит 94 печатных ASCII-символа без пробела: 26 заглавных + 26 строчных + 10 цифр + 32 знака. `\Z` запрещает дополнительные символы в конце, включая перевод строки. Наличие всех четырёх классов в каждом пароле исходным требованием не задано; при необходимости это отдельное уточнение политики.

`unique_last_password_count = 1` не позволяет пользователю завершить обязательную смену, повторно указав тот же временный пароль. Чтобы не вводить это дополнительное ограничение для сервисных пользователей, патч из раздела 5 исключает их и из этой проверки. Периодическое истечение паролей и блокировка за неактивность исходными требованиями не заданы; здесь они не включаются.

Обязательная смена срабатывает при создании пользователя с паролем и после административной установки нового пароля. Уже существующие пароли не становятся временными только от включения настройки. Для перевода существующего человеческого пользователя в этот процесс администратор выполняет согласованный сброс.

Источник поведения первой смены: [Keystone first use](https://docs.openstack.org/keystone/2025.1/admin/configuration.html#force-users-to-change-password-upon-first-use). История и самосмена: [SQL backend](https://docs.openstack.org/keystone/2025.1/_modules/keystone/identity/backends/sql.html#Identity.change_password).

## 5. Реализованный патч для исключения сервисных записей

### 5.1. Интерфейс расширения — НЕ штатная настройка

Boolean-опция `password_policy_exempt` (resource-option ID `PPEX`) хранится в существующей таблице Keystone. Отсутствие или `false` означает обычную политику. `true` отключает regex, историю и минимальный возраст пароля; JSON `null` удаляет опцию. Строка `"true"` и другие некорректные значения отклоняются API.

Для сервисной записи назначить все четыре options:

```json
{
  "user": {
    "options": {
      "password_policy_exempt": true,
      "ignore_change_password_upon_first_use": true,
      "ignore_lockout_failure_attempts": true,
      "ignore_password_expiry": true
    }
  }
}
```

Последние три опции штатные. Они отдельно исключают первую смену, блокировку и истечение. Новая опция не подменяет их. Другие options, включая MFA, сохраняются. `lock_password = true` по-прежнему запрещает самосмену.

### 5.2. Где проверяется политика и кто назначает исключение

База патча — официальный `stable/2025.1`, commit `537e65b2b1d4b8e0fe1faa09c8f882a6b2899b21`. Файл [патча Keystone](https://github.com/lebtmalorny-rgb/mimaric/blob/60bbc29354ee852cf70bed835235344a205f3468/keystone-password-policy-exempt.patch) содержит изменения API, resource options, SQL backend, policy, тестов и документации.

Для SQL проверка выполняется при записи пароля с актуальными options целевой записи. Обновление и самосмена используют блокировку строки в транзакции; кеш менеджера не даёт права обходить regex после отзыва исключения. При создании пароль и options передаются вместе. Снятие исключения и установка пароля одним запросом уже проверяют новый пароль как человеческий. Безусловный regex из JSON Schema самосмены перенесён в проверку с учётом пользователя; проверки типа/технической максимальной длины сохранены.

Включение, выключение и удаление опции в API дополнительно требуют `identity:manage_password_policy_exemption`; по умолчанию это `role:admin and system_scope:all`. Обычный project/domain admin не получает исключение только из-за роли. Для отдельной deployment identity Kolla настроить точечный policy override по UUID, как показано в [инструкции пакета](https://github.com/lebtmalorny-rgb/mimaric/blob/60bbc29354ee852cf70bed835235344a205f3468/README.md#4-кто-вправе-назначать-исключения). Существующие права create/update также обязательны. Назначение классификации журналируется без паролей.

Самосмена требует правильного старого пароля. Формат токенов, хеширование, штатный отзыв токенов и схема БД не менялись. Патч не делает автоматическую классификацию по имени, роли, HTTP-заголовку или источнику запроса.

### 5.3. Проверки и границы

Локальные API/SQLite-регрессии проверяют все три способа установки пароля, недостаточные права, некорректные options, history/minimum age, сохранение аутентификации и технических ограничений, отзыв токенов и устаревший кеш классификации. Точные команды и результаты — в [отчёте Keystone](https://github.com/lebtmalorny-rgb/mimaric/blob/60bbc29354ee852cf70bed835235344a205f3468/reports/keystone-implementation.md); интеграция SDK/Ansible — в [отчёте Kolla](https://github.com/lebtmalorny-rgb/mimaric/blob/60bbc29354ee852cf70bed835235344a205f3468/reports/kolla-implementation.md).

Это не заменяет приёмку образа с вашей MariaDB/Galera, несколькими workers и Horizon. Конкурентный порог lockout и поведение HA проверяются на стенде; алгоритм счётчика неудачных входов этим патчем не переработан.

## 6. Настройки Horizon

Файл `/etc/kolla/config/horizon/_9999-custom-settings.py`:

```python
ALLOW_USERS_CHANGE_EXPIRED_PASSWORD = True

# Общая проверка сложности в UI не должна блокировать сервисные записи.
# Для людей политику обеспечивает Keystone с проверкой целевой записи.
HORIZON_CONFIG['password_validator'] = {
    'regex': '.*',
    'help_text': 'Требования к паролю проверяются сервером Keystone.',
}
```

Не копировать человеческий regex в глобальный валидатор Horizon: формы администратора также используются для изменения сервисных записей. Подтверждение нового пароля и непустое поле остаются. Backend обязан отвергать слабый человеческий пароль даже при прямом API-запросе.

Значение `ALLOW_USERS_CHANGE_EXPIRED_PASSWORD = True` штатно. Путь первой смены: временный пароль → ответ Keystone о необходимости смены → форма Horizon → новый пароль → повторный вход. До смены обычная парольная аутентификация не выдаёт токен для работы с сервисами.

Источники: [Horizon expired password](https://docs.openstack.org/horizon/2025.1/configuration/settings.html#allow-users-change-expired-password), [Horizon password validator](https://docs.openstack.org/horizon/2025.1/configuration/settings.html#password-validator).

## 7. Сервисные пользователи и автоматизация Kolla-Ansible

### 7.1. Существующие записи

До включения политики штатные исключения можно назначить поддерживаемой командой:

```bash
openstack user set \
  --ignore-change-password-upon-first-use \
  --ignore-lockout-failure-attempts \
  --ignore-password-expiry \
  <SERVICE_USER_ID>
```

Для пользовательской опции после установки патча использовать `PATCH /v3/users/<SERVICE_USER_ID>` с JSON из раздела 5.1 через контролируемую административную автоматизацию. Штатного аргумента CLI `--password-policy-exempt` нет; не выдавать его за существующую команду. При чтении/обновлении options сохранить остальные ключи и проверить результат API.

Источник штатных флагов: [OpenStackClient user set](https://docs.openstack.org/python-openstackclient/2025.1/cli/command-objects/user-v3.html#user-set).

### 7.2. Новые записи и смена сервисных паролей

[Патч Kolla](https://github.com/lebtmalorny-rgb/mimaric/blob/60bbc29354ee852cf70bed835235344a205f3468/kolla-service-password-policy.patch) добавляет opt-in `keystone_service_password_policy_exempt: true` в `globals.yml`. При нём общая роль `service-ks-register` и отдельный Magnum trustee используют новый `kolla_service_user`; при `false` остаётся штатный модуль. Добавление неизвестного `options:` в vanilla `openstack.cloud.identity_user` не требуется.

Модуль отправляет пароль и все options в **одном** запросе при создании. При обновлении сохраняет unrelated options и отправляет итоговые options вместе с паролем, если нужна ротация. `update_keystone_service_user_passwords: false` сохраняет уже установленный пароль. Парольные задачи используют `no_log: true`, также при включённом debug.

Модуль размещается в смонтированной config-папке toolbox, сохраняя штатные Vault/auth/CA/mTLS механизмы. Пересборка toolbox не нужна. Требования к версиям коллекции/SDK, check mode и сборке приведены в [README пакета](https://github.com/lebtmalorny-rgb/mimaric/blob/60bbc29354ee852cf70bed835235344a205f3468/README.md).

Bootstrap/deployment identity, внешние скрипты и runtime-created Heat/Magnum identities требуют отдельной явной классификации. Если приложение само создаёт новые технические identities, оно должно передавать options в исходном запросе с разрешёнными правами. Патч Kolla охватывает свои регистрационные пути, а не произвольных producers. Личные административные записи не включать в сервисные исключения.

Не создавать пользователя с паролем под включённой политикой, чтобы пометить сервисным только после создания: regex уже мог отклонить пароль, а первая смена — сделать его временным.

## 8. Образ и порядок применения

1. Подготовить резервную копию исходных overrides и options без выгрузки паролей в отчёт.
2. Применить подготовленный патч к его точной базе, собрать и проверить Keystone-образ по [инструкции](https://github.com/lebtmalorny-rgb/mimaric/blob/60bbc29354ee852cf70bed835235344a205f3468/README.md), опубликовать неизменяемую версию.
3. Установить подготовленный патч Kolla и operator policy из раздела 7.2; проверить отдельную deployment identity.
4. Выбрать образ на deploy-узле в `globals.yml`, например:

```yaml
keystone_image: "registry.example.org/openstack/keystone"
keystone_tag: "2025.1-password-policy-1"
```

Имена — образец будущего собранного образа, не существующая публикация. Проверить, что более приоритетные переменные `keystone_service_tag` или `keystone_image_full` не перекрывают выбор. Сохранить digest фактически установленного образа на каждом узле.

5. Обновить все Keystone workers собственным образом при ещё выключенной человеческой политике. Не оставлять одновременно штатные workers и workers с новым API options при включённых исключениях.
6. Назначить и проверить исключения всем существующим сервисным записям.
7. Добавить настройки разделов 4 и 6.
8. В согласованное окно оператор выполняет на deploy-узле:

```bash
kolla-ansible -i /path/to/inventory prechecks --tags keystone,horizon
kolla-ansible -i /path/to/inventory reconfigure --tags keystone,horizon
```

Пути и стандартная команда подходят после проверки установленной версии Kolla. Повторный `reconfigure` включает регистрацию identities, поэтому исправление автоматизации должно предшествовать ему. Команды здесь приведены для оператора и при написании документа не выполнялись.

Если используются собственные host-specific overrides, проверить приоритет: `global.conf`, `keystone.conf`, `keystone/keystone.conf`, `keystone/<host>/keystone.conf`. Значения на всех узлах должны совпадать.

Ссылка на разрешение переменных образа: локальный defaults/main.yml (`kolla-ansible-pvs_1.0.0/ansible/roles/keystone/defaults/main.yml` в исходном архиве Kolla).

## 9. Повседневные действия

Административное создание и сброс человеческого пароля, ввод пароля интерактивно:

```bash
openstack user create --domain <HUMAN_DOMAIN> --password-prompt <USERNAME>
openstack user set --password-prompt <HUMAN_USER_ID>
```

Назначение проектов/ролей выполняется отдельно по существующей модели RBAC. Пользователь завершает смену через Horizon. Человеческие записи должны иметь `ignore_password_expiry = false` и `ignore_change_password_upon_first_use = false` либо не иметь этих опций.

Снятие блокировки администратором:

```bash
openstack user set --enable <HUMAN_USER_ID>
```

Keystone хранит счётчик неудачных попыток отдельно; нельзя определять наличие lockout только по выводу `enabled`. Штатное административное обновление `enabled` используется для снятия блокировки. Проверять результат новым входом. [Документация lockout](https://docs.openstack.org/keystone/2025.1/admin/configuration.html#setting-an-account-lockout-threshold).

Сервисные пароли ротируются отдельно с синхронным обновлением потребляющих сервисов. Освобождение от проверки не означает автоматическую смену всех текущих секретов.

## 10. Приёмка

Проверки выполнить на отдельных тестовых человеческой и сервисной записях, а не на рабочих сервисах. Сохранить UTC-время, user ID, узел, HTTP-код и результат без токенов и паролей.

| Проверка | Ожидаемый результат |
|---|---|
| Человеку установить 7 символов через create, update и self-service API | Отказ во всех случаях |
| Человеку установить допустимый пароль 8+ символов | Успех |
| Проверить заявленные 94 символа в разных позициях пароля | Символы не теряются при вводе, передаче и хранении |
| Создать человека с временным паролем | Новый обычный password token не выдаётся до смены |
| Пройти первый вход Horizon | Форма смены; повтор временного пароля отвергается; новый пароль работает |
| Сбросить человеческий пароль администратором | Снова требуется смена |
| 3 неправильных входа, затем правильный | Правильный вход успешен, счётчик сброшен |
| После сброса счётчика 4 неправильных входа, затем правильный | Правильный пароль не даёт войти до разблокировки |
| Ручная разблокировка / истечение 900 секунд | Новый вход успешен |
| Сервису установить непустой тестовый пароль вне regex через все три API-пути | Успех; история, первая смена и lockout не применяются согласно классификации |
| Несколько неправильных входов тестовой сервисной записью | Человеческий lockout не включается |
| Обычный пользователь пытается назначить исключение | Отказ |
| Повторная регистрация/ротация и добавление сервиса через Kolla | Исключения присутствуют до установки пароля и сохраняются |
| Попытки через разные Keystone workers и параллельные запросы | Проверен общий счётчик и фактический порог; нет обхода через другой worker |

Не приравнивать число нажатий кнопки Horizon к числу backend-аутентификаций: фиксировать реальные запросы. Настройка `4` сама по себе не доказывает строгий предел при конкурентных запросах; такую нагрузку проверять отдельно и исправлять обнаруженные гонки до приёмки.

Сброс пароля и lockout новых парольных входов не являются универсальным механизмом остановки всех существующих Horizon-сессий, Fernet-токенов, trusts и application credentials. Если требуется немедленно прекращать уже выданный доступ, это отдельный сценарий отзыва, который нужно определить и проверить.

## 11. Откат и статус проверки

Откат выполнить в порядке: вернуть предыдущую конфигурацию политики → применить ко всем workers → при необходимости вернуть исходный образ и автоматизацию. Возврат штатного образа при оставленном глобальном regex снова распространит проверку на сервисные записи.

Удаление `change_password_upon_first_use` не обязано отменять уже записанное истечение временного пароля. Не исправлять это прямым SQL: завершить штатную самосмену или выполнить контролируемый сброс после исправления options/политики.

Подготовлены патчи, выполнены локальные API/SQLite и SDK/Ansible проверки; результаты и известные исходные падения upstream-тестов перечислены в [отчётах](https://github.com/lebtmalorny-rgb/mimaric/tree/60bbc29354ee852cf70bed835235344a205f3468/reports/). Сборка Linux-образов, реальные настройки кластера, Horizon, MariaDB/Galera и HA-порог не проверялись. До инвентаризации всех producers и стендовой приёмки нельзя считать требование полным для конкретного развёртывания.

Для каталога пользователей см. [руководство LDAP: MS AD / FreeIPA](OPENSTACK_PASSWORD_POLICY_LDAP_AD_FREEIPA.md).
